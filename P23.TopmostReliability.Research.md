# P23-TOPMOST-001 — Topmost Reliability Research

**Investigation date:** 2026-11-26  
**Status:** Research only; exact root cause remains unproven.  
**Scope:** Historical Phase 2.3 evidence, current WinUI/controller/adapter code, and documented Microsoft window-ordering behavior.  
**Safety:** Read-only investigation. No source was changed, no app or verification script was run, no desktop settings were changed, and the native taskbar was not touched. GPT's M4 verification was not run or interfered with.

## Executive finding

`P23-TOPMOST-001` is still unresolved. The strongest historical evidence establishes that the *same Debug assembly* was sometimes observed with `WS_EX_TOPMOST` present (`EXSTYLE 0x108`) and sometimes without it (`EXSTYLE 0x100`); a debugger trace also captured a successful `HWND_TOPMOST` request on the correct HWND. This demonstrates inconsistent observed state, but none of the reports captures the exact operation that explains the transition or failure.

The current app already requests topmost through `OverlappedPresenter.IsAlwaysOnTop = true`. `AppWindow.Show(false)` is an explicit no-activation show, and surface-region updates do not intentionally reorder the window. Do not add a timer, activation-triggered “bring to top,” or duplicate native topmost mechanism on speculation. First capture a failing transition with timestamps and the actual window-ordering caller. If a repair is then justified, keep it in the adapter, preserve non-activation, and make it bounded and observable.

## Current architecture and call path

The project targets `net10.0-windows10.0.26100.0`, x64, and pins `Microsoft.WindowsAppSDK` `2.7.0` in `src\IslandTaskbar\IslandTaskbar.csproj`.

1. `App.OnLaunched` constructs `WindowsAppSdkIslandWindowAdapter` and `IslandWindowController`, then calls `Initialize()`.
2. `IslandWindowController.Initialize()` queries primary-display bounds, calls `ConfigureOverlay()`, calls `MoveAndResize()`, then `ShowWithoutActivation()`.
3. `WindowsAppSdkIslandWindowAdapter.ConfigureOverlay()` sets `OverlappedPresenter.IsAlwaysOnTop = true`; it then adjusts frame/extended styles, applies DWM attributes, and installs an initially empty region.
4. `ShowWithoutActivation()` calls `AppWindow.Show(false)`.
5. Layout changes flow through `App.OnSurfaceLayoutChanged` to `UpdateSurfaceRegion()`. The adapter applies a region/polygon; these methods contain no deliberate topmost/Z-order reassertion.
6. `MoveAndResize()` uses `AppWindow.MoveAndResize` and, for the measured client inset, `AppWindow.Move`. The inspected source contains no `AppWindow.MoveInZOrder*` call and no explicit `SetWindowPos(HWND_TOPMOST)` repair. The frame recalculation call includes `SWP_NOZORDER` and `SWP_NOACTIVATE`.

Relevant files: `src\IslandTaskbar\App.xaml.cs`, `src\IslandTaskbar\Controllers\IslandWindowController.cs`, `src\IslandTaskbar\Adapters\Implementations\WindowsAppSdkIslandWindowAdapter.cs`, and `src\IslandTaskbar\Adapters\Implementations\WindowsAppSdkDisplayService.cs`.

### Display and activation observations

- `WindowsAppSdkDisplayService` reads `DisplayArea.Primary.OuterBounds`; its source comment explicitly says it has no display-change listeners. `App.xaml.cs` and `IslandWindowController` show no display-change subscription. The controller reads the current primary bounds during initialization and again when processing layout updates. This means display/primary changes are not explicitly observed and recentering is not guaranteed. That is a **known coverage/positioning gap**, not evidence that display changes clear topmost status.
- `AppWindow.Show(false)` requests showing without activation. Foreground/activation and topmost grouping are different state. The startup-focus test must not use a foreground change as a proxy for topmost loss.
- The adapter's `SetWindowLongPtr(GWL_EXSTYLE, exStyle | WS_EX_LAYERED)` preserves the topmost bit present in the value it reads; by itself it does not explain an observed `0x108 → 0x100` loss. Its return value is not checked, so partial style setup can be silent, but the available reports do not link that to topmost failure.
- The app does not hide the native taskbar in the current prototype. Topmost investigation and recovery must not add taskbar manipulation.

## Windows API semantics and supported options

Microsoft Learn describes the contract; it cannot reveal which operation caused the historical failure on this machine.

1. **`OverlappedPresenter.IsAlwaysOnTop` is the current supported request.** Microsoft documents it as keeping the window on top of other windows. The same API docs state that when multiple windows are always-on-top, the window last activated or interacted with is on top. Thus “topmost” means the topmost Z-order group, not a guarantee of winning against every other topmost window.
2. **No activation is orthogonal.** `AppWindow.Show(Boolean)` documents `false` as showing without activating. Win32 topmost windows overlap non-topmost windows regardless of active/foreground state. Therefore `Show(false)` and a later normal foreground transition are not, on their own, explanations for a missing `WS_EX_TOPMOST` bit.
3. **`SetWindowPos` is a documented native ordering API.** Passing `HWND_TOPMOST` without `SWP_NOZORDER` makes a window topmost; `SWP_NOACTIVATE` preserves non-activation, and `SWP_NOMOVE | SWP_NOSIZE` avoid geometry changes. `HWND_NOTOPMOST` explicitly demotes. `SWP_NOZORDER` means the requested insertion order is ignored. This is a supported one-shot corrective primitive *if* a real demotion is captured and the owner approves the implementation; it is not evidence that a second setter is needed now.
4. **Other Z-order helpers are not equivalent.** `AppWindow.MoveInZOrder*` methods deliberately move a window in the Z-order, and Microsoft notes they still take effect even when `IsAlwaysOnTop` is true. `BringWindowToTop` is not a persistent topmost request. `SetForegroundWindow` is a focus operation, not a safe topmost recovery mechanism.
5. **Display notifications are distinct from ordering.** Win32 documents `WM_DISPLAYCHANGE` for display-resolution changes and `WM_DPICHANGED` for per-monitor DPI changes. The current source has no display listener, so geometry must be tested separately. Neither documented message states that it removes topmost state.
6. **Expected boundaries:** repository architecture explicitly scopes the topmost requirement to normal desktop use, subject to secure-desktop and exclusive-fullscreen behavior (`ARCHITECTURE.md` §4.1). Do not use UAC secure desktop or exclusive-fullscreen overlays as a general topmost acceptance test.

## Recommended minimal remediation and recovery

### Before changing code

1. Reproduce only on the approved target build with the same signed-off launch path and a known ordinary foreground window. Capture the island's exact root HWND/PID and timestamped checkpoints: before/after setting `IsAlwaysOnTop`, after native style setup, before/after `Show(false)`, after move/resize, after region updates, and after foreground changes.
2. At every checkpoint record the presenter property, `GWL_EXSTYLE` including the `WS_EX_TOPMOST` mask, the actual topmost/non-topmost Z-order group and neighboring top-level HWNDs, foreground HWND, visibility, bounds, and hit-test owner. A style bit alone or a single Z-rank alone is insufficient to distinguish “lost topmost” from “another topmost peer is above it.”
3. If a failing transition recurs, capture a Win32k window-position trace that attributes the operation/caller and correlate it with the observer. The previous report says this needed administrator trace-control permission; the application itself must remain at normal user integrity. Do not infer the caller from WinEvent notification provenance alone.

### Conditional code change, only after attribution

- If a later in-app call demotes the window, correct that call at its source; do not add a second mechanism.
- If the supported presenter setter is shown to leave the owned HWND non-topmost in the failing path, first confirm the pinned Windows App SDK `2.7.0` behavior. With an approved design decision, a single adapter-boundary `SetWindowPos(HWND_TOPMOST, ..., SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE | SWP_NOOWNERZORDER)` may be evaluated as an idempotent corrective request. The actual call must not include `SWP_NOZORDER`; it must check its Boolean result and verify the resulting style/order. Do not add handwritten P/Invoke; use the existing CsWin32 pattern.
- Do not add periodic Z-order polling/reassertion, delayed timers, focus-event reassertion, repeated `IsAlwaysOnTop` toggles, `BringWindowToTop`, or `SetForegroundWindow`. Those approaches can mask the actual caller, disrupt peer topmost windows, or steal activation without proving the root cause.
- `CONVENTIONS.md` §E.3 still says OD-011 (controller form/placement and windowing logic) is open and bars new topmost/anchoring/display-change Win32 logic until an architecture update. Resolve that decision before implementing any new native recovery path.

### Safe recovery behavior

If an accepted implementation later detects a confirmed loss while the app owns a valid HWND and is in normal desktop use, permit at most a bounded, non-activating corrective request and immediately verify/report its result. On failure, record a meaningful local diagnostic and stop retrying; do not force foreground, change display settings, hide/modify the native taskbar, restart Explorer, or enter a retry loop. Leave the existing taskbar and normal desktop recovery unaffected. For another topmost window above the island, do not automatically fight it: apply the documented topmost-peer policy and user interaction semantics.
