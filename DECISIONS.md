## 2. Decision Process

### 2.1 Statuses

| Status | Meaning |
|---|---|
| **Proposed** | Drafted and under review. Not binding. |
| **Approved** | Approved by the Product Owner. Binding on all agents and contributors. |
| **Open** | A question that is recognized but not yet decided. Not binding in any direction. |
| **Superseded** | Replaced by a later entry. Kept for traceability and no longer binding. |

### 2.2 Approving a decision

1. Anyone, including agents through a Decision Request (`AGENT.md` §16), may raise a question or proposal. Agents do not edit this file unless assigned.
2. The Chief Engineer reviews technical decisions and recommends a position.
3. The **Product Owner approves**. Only then does an entry become **Approved**.
4. Every new entry carries: unique ID, title, status, decision statement, reasoning, consequences for implementation, and **alternatives considered** (`ARCHITECTURE.md` §13).
5. Product, scope, visual, and identity decisions are the Product Owner's. Changes to the technology stack additionally require an ADR-style entry here (`ARCHITECTURE.md` §0).
6. Validation spike results are recorded in Section 5. A spike result becomes an Approved decision only through steps 2 and 3.

### 2.3 Changing or superseding a decision

- Never rewrite the decision statement of an Approved entry. Only typographical corrections are allowed in place, and they are logged.
- To change a decision: add a **new** entry that states what it replaces and why, mark the old entry **Superseded by D-xxx** (keep its text), and add a change-log line (Section 8).
- Update every affected project document in the same change, and `CHANGELOG.md` for material version changes (`ENV.md` §11).
- Scope changes also follow `SCOPE.md` §9 and must be reflected in `SCOPE.md`, `PRD.md`, and `TASKS.md`.

### 2.4 Resolving an open decision

Create a new Approved `D-xxx` entry that cites the `OD-xxx` entry, then mark the OD entry **Superseded by D-xxx**. Do not delete it.

### 2.5 Numbering

`D-xxx` for approved decisions and `OD-xxx` for open ones. IDs are never reused. `ADR-xxx` identifiers in `ARCHITECTURE.md` §13 are cross-referenced in Section 7, not duplicated.

## 3. Approved Decisions

All entries below: **Status:** Approved. **Approved by:** Product Owner. **Recorded:** 2026-11-19. Reasoning is taken from the referenced documents; no additional technical justification has been added.

### D-001 — Native Windows Application

**Decision:** IslandTaskbar is a native Windows desktop application. It is not a website, an Electron app, or a cloud service.

**Reasoning:** `PRD.md` §1 defines a native Windows 11 desktop application. `PRD.md` §7 and §11 and `SCOPE.md` §4 exclude Electron, web technologies, and any non-native UI stack.

**Consequences:**
- No Electron, browser shell, web UI, or non-native UI framework, ever (`ARCHITECTURE.md` §0).
- No cloud account, online service, or backend is required for core operation.
- Not a mobile, web, or macOS product (`SCOPE.md` §4).

**References:** `PRD.md` §1, §7, §11; `SCOPE.md` §4, §5; `ARCHITECTURE.md` §0, §2.

---

### D-002 — One Visible Taskbar

**Decision:** Only IslandTaskbar is visible during normal operation. The original Windows taskbar is hidden, not shown alongside the replacement. It may remain available as a system fallback.

**Reasoning:** "One visible taskbar" is the first product principle (`PRD.md` §5) and the goal of US-002. The native taskbar stays part of the Windows shell and is hidden while the replacement is active (`PRD.md` §1).

**Consequences:**
- Two visible taskbars must never appear, for any reason.
- The native taskbar is hidden, not deleted or permanently modified, and must be restorable (US-002, US-003).
- Auto-hide must not be substituted if it lets the native taskbar reappear on pointer movement (`ARCHITECTURE.md` §5.1).
- "Fallback" means the native taskbar can be restored. It does not mean it is displayed concurrently.
- The hiding mechanism is not yet chosen (OD-008).

**References:** `PRD.md` §1, §5; `SCOPE.md` §2.1, §3; `USER_STORIES.md` US-002, US-003; `ARCHITECTURE.md` §5.1.

---

### D-003 — Independent Replacement Architecture

**Decision:** The application runs independently. It does not use forced Explorer injection and does not depend on Windhawk. IslandTaskbar owns its visible interface.

**Reasoning:** Recorded as ADR-001 and ADR-002 in `ARCHITECTURE.md` §13. `PRD.md` §1 and §11 and `SCOPE.md` §4 exclude injecting into or patching `explorer.exe` as the primary architecture.

**Consequences:**
- No injection into, patching of, or hooking of `explorer.exe`, and no reliance on undocumented Explorer internals as the primary approach.
- Windhawk is never a runtime or installation dependency (`ARCHITECTURE.md` §0, §2, §8).
- Windows continues to provide Start, Search, window management, and system services; IslandTaskbar invokes them rather than reimplementing them (`ARCHITECTURE.md` §6).
- Use of an undocumented Windows behavior needs Chief Engineer approval and a decision entry (`AGENT.md` §7).

**References:** `ARCHITECTURE.md` §0, §1, §13 (ADR-001, ADR-002); `PRD.md` §1, §11; `SCOPE.md` §1, §4; `USER_STORIES.md` US-001.

---

### D-004 — Technology Stack

**Decision:**
- Language: C#
- Runtime: .NET 10 LTS
- UI framework: WinUI 3
- Windows App SDK: 2.7.0 (stable)
- Native integration: Win32 interop where necessary
- Interop declarations: CsWin32 preferred for appropriate type-safe interop

Approved versions are those documented in `ARCHITECTURE.md` §2 and `ENV.md` §0, §3, §6:

| Item | Approved baseline |
|---|---|
| .NET SDK | `10.0.404`, pinned in `global.json` with `rollForward: latestPatch` |
| .NET runtime servicing level | `10.0.15` |
| Windows App SDK | `2.7.0` stable, pinned in the project file |
| Windows SDK | `10.0.26100.0` family or later |
| Initial build architecture | `x64` (ARM64 after core validation) |

**Reasoning:** `ARCHITECTURE.md` §2 selects .NET 10 LTS as the preferred LTS track for a long-lived desktop application and states that .NET 11 is STS and unsuitable. Windows App SDK 2.7.0 is the current stable release supporting Windows 11 26H2.

**Consequences:**
- No other .NET version (8, 9, 11), no Preview or Experimental Windows App SDK APIs in production paths, and no third-party package without a documented reason.
- Changing any part of the stack requires a written decision entry and Product Owner approval, plus `CHANGELOG.md` updates (`ARCHITECTURE.md` §0; `ENV.md` §0, §11).
- Win32 calls go through adapters (ADR-005); the presentation layer never calls Win32 directly.
- Exact package versions and the target framework moniker are confirmed at project creation (OD-023).
- **Flagged:** `PRD.md` §7 and `SCOPE.md` §5 still say .NET 8 (C-01). CsWin32 wording differs between documents (C-09).

**References:** `ARCHITECTURE.md` §2, §13 (ADR-003, ADR-004, ADR-005); `ENV.md` §0, §3, §6, §11.

### D-005 — No Database or Cloud Backend

**Decision:** IslandTaskbar is a local desktop application. Local settings and JSON configuration are used where appropriate. No database, Supabase, PostgreSQL, or cloud backend is currently required.

**Reasoning:** `DATABASE_SCHEMA.md` §2 records that current requirements need no relational database, remote database, backend, cloud account, or internet connection. `ARCHITECTURE.md` §7 uses versioned JSON files with atomic writes (ADR-006, ADR-007).

**Consequences:**
- Do not create SQL schemas, migrations, or database infrastructure, and do not use SQLite, LiteDB, or any embedded or remote database.
- Persist preferences and pins as versioned JSON in the per-user application data directory, written atomically, validated on load, with safe defaults (`DATABASE_SCHEMA.md` §0, §5).
- Do not describe the JSON files as a "database."
- Reconsideration requires an approved requirement and the process in `DATABASE_SCHEMA.md` §6, recorded as a new decision here.
- Add no telemetry or remote sync as a side effect (`DATABASE_SCHEMA.md` §7).

**References:** `DATABASE_SCHEMA.md` §0, §2, §3, §5, §6, §9; `ARCHITECTURE.md` §7, §13 (ADR-006, ADR-007); `ENV.md` §7, §8.

### D-006 — First-Run Experience

**Decision:** US-000 (first-run experience) is part of Release 1. First-run completion state is stored locally, not in a database.

**Reasoning:** US-000 requires that the user understands what will change and how to restore the native taskbar before anything is altered, and that this explanation does not repeat on later launches.

**Consequences:**
- On first launch the user sees what IslandTaskbar does, what will change, and how to exit and restore the native taskbar, **before** the native taskbar is hidden.
- The app must not hide the native taskbar silently on first run.
- Completion state is stored locally in line with D-005.
- US-000's acceptance criteria are part of Release 1 acceptance.
- **Flagged:** `SCOPE.md` §3 and `PRD.md` §10 do not list US-000; `DATABASE_SCHEMA.md` §4 defines no first-run field and forbids inventing files (C-02). Do not add a file or field until `DATABASE_SCHEMA.md` is updated and approved (OD-012).

**References:** `USER_STORIES.md` US-000, §6; `SCOPE.md` §3; `DATABASE_SCHEMA.md` §0, §4.

---

### D-007 — Live Internet Speed Meter

**Decision:** The live internet speed meter is approved for Release 3. It must display actual download and upload throughput and never simulated values.

**Reasoning:** `PRD.md` §9.3, `SCOPE.md` §3, and US-025 place live network upload and download rates in the later releases and require rates derived from measured network counters.

**Consequences:**
- Do not start it until Release 1 and Release 2 acceptance criteria are fully met.
- Values come from measured data. When unavailable, show "unavailable"; never fabricate a number (US-025).
- Sampling must be bounded and must not add unnecessary CPU or battery cost (`ARCHITECTURE.md` §9).
- The measurement mechanism is not yet decided (OD-013).
- **Flagged:** `ARCHITECTURE.md` §3.3 lists `INetworkStatusService`, including transfer-rate metrics, as Release 2 (C-04).

**References:** `PRD.md` §9.3; `SCOPE.md` §3; `USER_STORIES.md` US-025; `DESIGN_SYSTEM.md` §9, §13; `ARCHITECTURE.md` §3.3, §9.

### D-008 — DPI Compatibility

**Decision:** The UI must be validated from 100% through 200% Windows display scaling.

**Reasoning:** `DESIGN_SYSTEM.md` §5 requires typography to be checked at 100%, 125%, 150%, and 200%. US-014 requires the interface to stay positioned and usable across supported scaling settings.

**Consequences:**
- Layout, text, icons, and hit targets are validated across 100% through 200% scaling.
- Reports must state exactly which scaling levels were tested. A claim of DPI compliance on fewer levels would not satisfy this decision.
- Use DIPs for layout; physical pixels only at Win32 boundaries (`DESIGN_SYSTEM.md` §11).
- **Flagged:** the Release 1 gate in `SCOPE.md` §3 names only 100% and 125% at 1080p and 1440p (C-03).

**References:** `DESIGN_SYSTEM.md` §5, §11, §15; `USER_STORIES.md` US-014; `SCOPE.md` §3.

### D-009 — Island Window Controller

**Decision:** The architecture must include a dedicated controller or adapter for:
- topmost behavior;
- monitor anchoring and positioning;
- window size and lifecycle;
- hit-testing and click-through behavior;
- DPI and display changes.

**Reasoning:** These responsibilities are Windows-level window behavior required by `ARCHITECTURE.md` §4, but no component in the current architecture owns them.

**Consequences:**
- `ARCHITECTURE.md` §3.3 and §3.4 must be updated to include it (C-05).
- Until then, do not implement these Win32 operations ad hoc, and do not place them in the presentation layer (`ARCHITECTURE.md` §0, §3.1).
- Its name, interface, layer placement, and relationship to `IDisplayService` and `DisplayManagerService` are open (OD-011).
- Its click-through and anchoring behavior must be validated on the target build (OD-010).

**References:** `ARCHITECTURE.md` §0, §3.1–3.4, §4, §11; `AGENT.md` §17.

---

### D-010 — Native Taskbar Recovery

**Decision:** Before native taskbar hiding is implemented, a reliable manual and automatic recovery strategy must be documented and tested.

**Reasoning:** The native taskbar must be restored on normal exit and recoverable after a crash or force-kill (`SCOPE.md` §3; US-003). `ARCHITECTURE.md` §5.2 states a `finally` block is not sufficient and calls for a documented manual recovery method.

**Consequences:**
- Production taskbar-hiding code is not written until the strategy exists in writing and has been tested.
- The strategy covers normal exit, crash, and force-kill, and includes a manual method that works without restarting Windows (US-003).
- Any change touching lifecycle, visibility, or recovery is tested for normal exit and forced termination.
- **Flagged (Unresolved interaction):** SPIKE-001 and SPIKE-002 must run taskbar-hiding experiments to learn what recovery requires, which is in tension with this decision (C-06). The document that holds the strategy is also unspecified (OD-009). Until the Product Owner clarifies, any run of hiding code, spike or otherwise, requires the authorization and recovery plan in D-012.

**References:** `SCOPE.md` §3, §9; `USER_STORIES.md` US-003; `ARCHITECTURE.md` §5.2, §11, §13 (ADR-009).

---

### D-011 — Git Safety

**Decision:** Coding agents must not push, force-push, reset, clean, delete branches, rewrite history, or run any other destructive Git command without explicit user approval.

**Reasoning:** Protects the Product Owner's repository and work from irreversible agent actions. This was approved as a project rule by the Product Owner.

**Consequences:**
- Approval is explicit and per action. A general task assignment is not approval.
- Applies to every form of `git reset`, `git clean`, history rewrites, branch or tag deletion, and force pushes.
- Agents may still inspect state and make small, focused local commits when assigned (`AGENT.md` §13).
- **Flagged:** `AGENT.md` §13 names `git reset --hard` only and permits no pushes by default; it must be aligned to cover all resets (C-07).

**References:** `AGENT.md` §13; `ENV.md` §4.

---

### D-012 — Taskbar-Hiding Safety

**Decision:** Never execute taskbar-hiding code unattended. Require explicit user authorization and a documented recovery plan before testing it.

**Reasoning:** Taskbar-hiding code changes the real desktop. A failure can leave the user without a usable taskbar (`PRD.md` §4.2; US-003).

**Consequences:**
- No unattended, scheduled, looped, background, or CI execution of code that hides the native taskbar.
- Each test run needs explicit authorization from the user and a documented recovery plan beforehand.
- This applies to validation spikes (SPIKE-001 to SPIKE-004) as well as production code.
- No documented manual recovery procedure exists yet, so no hiding code may be run until one does (C-14).
- **Flagged:** `AGENT.md` §11 asks only for a statement of how the taskbar will be restored and a ban on unattended runs. D-012 is stricter and prevails (C-07).

**References:** `AGENT.md` §11; `ARCHITECTURE.md` §5, §11; `USER_STORIES.md` US-003.
